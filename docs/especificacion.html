0. Cómo usar este documento

  1. Este documento manda. Si el código y el documento discrepan, se corrige el código, o se cambia primero el documento mediante un cambio explícito (ver §24).
  2. Palabras normativas: DEBE = obligatorio. NO DEBE = prohibido. DEBERÍA = recomendado, con excepción justificada. PUEDE = opcional.
  3. Cada requisito tiene un ID (RF-xxx funcional, RN-xxx no funcional, RA-xxx regla de arquitectura, RP-xxx requisito de plataforma HTTP). Los commits y PRs referencian los IDs.
  4. No se fijan versiones de dependencias aquí. Al iniciar cada fase se usan las últimas versiones estables compatibles y se fijan en Cargo.lock. Las dependencias cuyo comportamiento cambia entre versiones mayores (Axum, Prisma CLI) están marcadas con ⚠️ en la lista de verificaciones (§22).
  5. MSRV: Rust 1.94 (edición 2024), requerido por SQLx 0.9.

1. Visión y principios

Visión. Un framework REST para Rust con la ergonomía de NestJS y el minimalismo de las Minimal APIs de .NET, que guía al desarrollador hacia una organización DDD sin obligarlo a usar patrones avanzados.

Principios de diseño

#PrincipioConsecuencia
P1Simple primeroUn crate, un binario, sin buses ni microservicios en el alcance actual.
P2El dominio no conoce HTTP ni SQLdomain.rs no importa axum, sqlx ni nada de rdd::http.
P3Núcleo mínimo, extras como paquetesCORS, logging, Prisma son crates separados que se añaden con cargo add.
P4El núcleo no depende de ningún servidor HTTPAxum es una *plataforma* intercambiable detrás de la interfaz Platform (§4.4), igual que platform-express/platform-fastify en NestJS.
P5Errores clarosLas macros producen diagnósticos accionables con código (§8.7).
P6Magia acotadaLas macros generan código predecible y documentado (§8); no hay reflexión ni comportamiento oculto en tiempo de ejecución.
P7Honestidad técnicaLo que Rust no permite (reflexión, DI resuelta por tipos en tiempo de ejecución) se documenta, no se simula.

2. Alcance

2.1 Dentro del alcance (fases 0.1 a 0.4)

  • Servidor REST con controladores declarativos por macros, sobre una interfaz de plataforma (§4.4). Axum es la plataforma por defecto (rdd-axum).
  • Building blocks DDD mínimos: Aggregate, Service, Repo<T>, Error de dominio.
  • Inyección de dependencias (singleton) por contenedor.
  • Sistema de middlewares propio del núcleo: globales, por módulo, por controlador y por ruta. Las capas Tower se admiten como opción de la plataforma Axum (RF-089).
  • Suite de conformidad de plataformas (§4.5) y, en la fase 0.5, una segunda plataforma (rdd-hyper) que valide la abstracción.
  • Crates externos rdd-cors y rdd-logger.
  • Persistencia multi-motor vía adaptadores: el núcleo define el puerto DbAdapter y cada motor vive en su propio crate (§12). SQLite se incluye como adaptador predeterminado para proyectos locales; PostgreSQL cuenta con adaptador y MySQL, MongoDB, Redis y MSSQL quedan para fases posteriores.
  • Migraciones y esquema con Prisma CLI y generación de código Rust a partir de schema.prisma.
  • CLI rdd para scaffolding y ejecución.

Por qué hay un crate rdd-core y otro rdd. Si el núcleo se llamara rdd y además incluyera rdd-axum como feature, habría una dependencia circular (rdd-axum necesita el núcleo). Por eso el núcleo es rdd-core y rdd es una fachada que lo re-exporta junto con las macros y activa la plataforma por feature. El usuario solo declara rdd (y los paquetes opcionales como rdd-cors).

# Cargo.toml del usuario
rdd      = "..."                          # axum + sqlite por defecto (§12.6)
rdd-cors = "..."
uuid     = { version = "1", features = ["v4", "serde"] }   # el id del agregado (§7.2)
# o, sin Axum:
# rdd = { version = "...", default-features = false, features = ["hyper", "sqlite"] }

4.4 Interfaz de plataforma (modelo "adaptador sobre el router del servidor")

El núcleo define qué es una aplicación HTTP (rutas como datos, con middlewares ya compuestos). La plataforma solo sabe servirla.

// rdd-core
pub type Request   = http::Request<bytes::Bytes>;     // cuerpo ya en memoria (RP-002)
pub type Response  = http::Response<bytes::Bytes>;
pub type BoxHandler = Arc<dyn Fn(Request) -> BoxFuture<'static, Response> + Send + Sync>;

pub struct RouteDef {
    pub method:  Method,
    pub path:    String,              // SIEMPRE sintaxis "/:id" (RP-003); es `String` porque la
                                      // ruta final es `prefijo + ruta` y se calcula al montar (RF-051)
    pub handler: BoxHandler,          // incluye su cadena completa de middlewares
}

pub struct Limits {
    pub body_limit_bytes: usize,      // RF-017
    pub shutdown_grace:   Duration,   // RP-009
}

pub struct HttpApp {
    pub routes:   Vec<RouteDef>,
    pub fallback: BoxHandler,         // decide 404 o 405 (RP-007); también envuelto por middlewares globales
    pub limits:   Limits,
}
impl HttpApp {
    /// Enrutado y ejecución sin servidor: usado por TestApp y por plataformas sin router propio (RP-014).
    pub async fn dispatch(&self, req: Request) -> Response;
}

pub trait Platform: Send + 'static {
    fn name(&self) -> &'static str;
    fn serve(self, app: HttpApp, listener: tokio::net::TcpListener, shutdown: ShutdownSignal)
        -> BoxFuture<'static, Result<()>>;
}

App::run(addr) usa la plataforma por defecto; App::run_on(plataforma, addr) usa la indicada:

App::new().module(tasks::module()).run("0.0.0.0:3000").await;                          // Axum (feature por defecto)
App::new().module(tasks::module()).run_on(HyperPlatform::new(), "0.0.0.0:3000").await; // plataforma propia

4.5 Suite de conformidad (rdd-platform-tests)

Una abstracción con un solo adaptador tiende a copiar la forma de ese adaptador. La suite impide eso: toda plataforma debe pasar los mismos casos contra el mismo HttpApp.

// en el crate de cada plataforma, como test de integración:
#[tokio::test]
async fn conformance() {
    rdd_platform_tests::run_all(|| AxumPlatform::new()).await;
}

La suite levanta la plataforma en un puerto efímero (127.0.0.1:0, por eso el núcleo abre el TcpListener, §4.4) y ejecuta peticiones HTTP reales.

5. Estructura de un proyecto de usuario

La estructura conserva módulos por dominio y aplica una organización DDD minimalista. Cada módulo usa las cuatro capas estándar; la adaptación a Rust se documenta aquí para que el scaffold sea determinista:

  • x.y.ts → x_y.rs: el punto no es válido en un identificador de módulo Rust.
  • __tests__/ → tests/: evita el aviso non_snake_case de rustc.
  • external-services/, payment-gateways/ → external_services/, payment_gateways/.
  • src/test/ y test/ → tests/ en la raíz: es el único directorio de tests de integración que cargo reconoce.
  • .prettierrc → rustfmt.toml; .eslintrc.json → clippy.toml; tsconfig.json → Cargo.toml (edition + rust-version) y rust-toolchain.toml (perfil y componentes).
  • rust-toolchain.toml NO fija channel: un canal pinned obliga a rustup a descargar otro toolchain y el proyecto dejaría de compilar sin red, lo que rompería RF-143. El mínimo soportado lo declara rust-version en Cargo.toml.
  • Cada módulo se organiza en cuatro capas: domain/, application/, infrastructure/ y presentation/. El CLI usa el singular para el archivo del agregado en domain/ y conserva el plural para las otras capas.

Ejemplo de código generado por #[service] (referencia normativa de forma, no de nombres internos):

// El usuario escribe:
#[service]
pub struct TaskService { repo: Repo<Task> }

// La macro genera (simplificado):
impl ::rdd::di::FromContainer for TaskService {
    fn from_container(c: &::rdd::di::Container) -> ::rdd::Result<Self> {
        Ok(Self { repo: c.resolve::<Repo<Task>>("TaskService", "repo")? })
    }
}
// Extractor propio del núcleo (no depende de ninguna plataforma), con la firma
// de RF-057: `Ctx` y `Bind`, no un `Request` suelto.
impl ::rdd::http::FromRequest for TaskService {
    async fn from_request(ctx: &::rdd::http::Ctx, _bind: ::rdd::http::Bind) -> ::rdd::Result<Self> {
        ctx.resolve::<Self>()
    }
}

Las dos impls son por tipo, nunca blanket. #[controller] convierte cada parámetro en ::rdd::api::extract::<T>(…), que exige T: FromRequest (RF-057). Un impl<T: FromContainer> FromRequest for T solaparía con las impls locales de Json<T>, Path<T>, Query<T>, Header<T> y Ext<T>: Rust no razona en negativo, así que no puede demostrar que esos tipos nunca implementarán FromContainer y rechaza el blanket con E0119. Por eso #[service] emite la impl del tipo concreto, y por eso el service llega al handler como svc: TaskService sin que el controller nombre el contenedor.

Mientras #[service] no exista (RF-006), el scaffold escribe esas dos impls a mano en modules/<m>/mod.rs, con la misma forma que la macro emitirá. Un service cuya única dependencia es Repo<T> no necesita entrada en providers: del módulo: App::build() registra el valor Db y Repo<T>: FromContainer lo lee (§12.1), así que from_container se limita a c.resolve::<Repo<T>>("TaskService", "repo"). El singleton de RF-020 es el adaptador —el pool vive en Db— y el service es un handle sin estado que se reconstruye por petición a partir de él; registrar el service como provider sería redundante y obligaría a declarar Repo<T> como dependencia del grafo, cuando no es un valor registrado sino un tipo resoluble.

Por qué en mod.rs y no en la capa del service. Las dos impls nombran a la vez rdd::http (que RA-002 prohíbe en application/) y el adaptador de infrastructure/ (que RA-002 también prohíbe). modules/<m>/mod.rs es la raíz de composición del módulo —el equivalente a tasks.module.ts— y no está dentro de ninguna de las cuatro capas, así que RA-001, RA-002 y RA-003 no le aplican: puede importar las cuatro para cablearlas. Poner las impls allí no relaja ninguna regla; es el único lugar del módulo donde el cableado es legal. La regla de huérfanos lo permite porque el tipo es local al crate. Cuando #[service] llegue, emitirá las mismas dos impls en ese mismo archivo.

// #[controller("/tasks")] impl TaskController { #[get("/")]
//     async fn list(svc: TaskService) -> Result<Vec<Task>> { ... } }
impl TaskController {
    #[doc(hidden)]
    #[allow(non_snake_case)]
    pub fn __rdd_route_list() -> ::rdd::http::RouteDef {
        ::rdd::api::route_def(
            ::rdd::http::Method::GET,
            "/tasks",                       // prefijo + ruta, normalizada (RF-051)
            ::rdd::http::StatusCode::OK,    // estado base según verbo/unidad (RF-053)
            ::std::vec![],                  // #[middleware] de la ruta, en orden (§11.3)

                let svc = ::rdd::api::extract::<TaskService>(&__rdd_ctx, ::rdd::http::Bind::none()).await?;
                TaskController::list(svc).await
            },
        )
    }

    /// RF-056: el único código público generado además de los handlers.
    pub fn routes() -> ::std::vec::Vec<::rdd::http::RouteDef> {

11. Sistema de middlewares

11.1 Modelo

Un middleware es una función asíncrona sobre los tipos del núcleo (Request, Next, Response) que devuelve una respuesta o un Error. El núcleo compone la cadena completa antes de entregar el handler a la plataforma (RP-005), por lo que el orden y la semántica son idénticos en cualquier plataforma.

pub trait Middleware: Send + Sync + 'static {
    fn handle(&self, req: Request, next: Next)
        -> impl Future<Output = Result<Response>> + Send;
}

Compatibilidad con Tower: el trait Middleware NO depende de Tower. Las capas Tower existentes se pueden usar solo con AxumPlatform y envuelven por fuera toda la cadena de rdd (RF-089).

11.2 Formas de registro

// A. Global
App::new()
    .middleware(Cors::permissive())
    .middleware(Logger::default())

// B. Función (sin trait ni boilerplate)
.middleware(fn_middleware(|req, next| async move {
    tracing::info!("{} {}", req.method(), req.uri());
    next.run(req).await
}))

// C. Capa Tower: es una opción de la plataforma Axum, no de App (RF-089)

11.5 Crate rdd-cors

Implementación propia sobre el trait Middleware del núcleo (sin Tower), de modo que funciona igual en cualquier plataforma. Sigue el protocolo CORS del estándar Fetch.

// Desarrollo: cualquier origen. Infallible, pero avisa en release (RF-091).
Cors::permissive()

// Seguro por defecto: el builder acumula y `build()` valida (RF-090, RF-092).
Cors::new()
    .allow_origin("https://miapp.com")
    .allow_methods([Method::GET, Method::POST, Method::PUT, Method::DELETE])
    .allow_headers([header::CONTENT_TYPE, header::AUTHORIZATION])
    .expose_headers(["x-request-id", "ratelimit-remaining"])
    .allow_credentials(true)
    .max_age(Duration::from_secs(3600))
    .build()?

// Lee la sección [cors] del rdd.toml del directorio actual (§15, RF-093).
Cors::from_config()?

Dos tipos, no uno: Cors::new() devuelve un builder que acumula sin validar, y su build() devuelve Result<Cors, CorsConfigError>. Cors es el middleware ya validado y lo único que App::middleware acepta. Separarlos permite encadenar los setters sin un ? por línea y, a la vez, rechazar en la construcción una combinación que el estándar prohíbe (RF-092). allow_origin se puede llamar varias veces: cada llamada añade un origen a la lista. permissive() devuelve Cors directamente y from_config() devuelve Result<Cors, CorsConfigError>, porque en un caso no hay nada que validar y en el otro los valores vienen de un archivo.

from_config() lee el rdd.toml del directorio actual (§15). Sin sección [cors] equivale a Cors::new().build(): deniega todo origen cruzado (RF-090), nunca abre por omisión. Un rdd.toml que no existe se trata igual que uno sin la sección; uno que existe pero no parsea es un error, porque ahí sí hay una intención de configurar que no se puede cumplir. Un método o una cabecera que no parsea produce error nombrando el valor inválido. La configuración CORS es una decisión de seguridad: no puede fallar en silencio ni resolverse en la primera petición.

Tres detalles que el builder tiene que resolver para no dejar huecos:

  • Sin allow_methods, el preflight anuncia los métodos safelisted del estándar Fetch: GET, HEAD, POST. Sin allow_headers anuncia accept, accept-language, content-language, content-type, que son las cabeceras safelisted. RF-096 exige que ambas cabeceras estén presentes, así que omitirlas no es una opción; anunciar la lista safelisted es el mínimo honesto.
  • Vary: Origin se añade también al origen denegado. No es una cabecera Access-Control-* ni concede nada: sin ella una caché intermedia podría servir la respuesta denegada a un origen que sí estaba permitido.
  • Una petición normal con credenciales lleva Access-Control-Allow-Credentials: true además del origen reflejado; sin esa cabecera el navegador descarta la respuesta aunque el origen esté en la lista.

12. Persistencia

La persistencia es multi-motor vía adaptadores, con el mismo contrato que las plataformas de §4.4: el núcleo define el puerto y cada motor lo implementa en su propio crate. ADR-16 sustituye a ADR-10.

12.1 El puerto DbAdapter y Repo<T>

Repo<T> no cambia de cara al usuario: es un handle con los seis métodos.

impl<T: Aggregate + Persist> Repo<T>
where
    T::Id: Into<Value>,
{
    pub fn new(adapter: Arc<dyn DbAdapter>) -> Self;
    pub async fn get(&self, id: T::Id) -> Result<T>;               // NotFound si no existe
    pub async fn find(&self, id: T::Id) -> Result<Option<T>>;
    pub async fn all(&self) -> Result<Vec<T>>;
    pub async fn save(&self, aggregate: &T) -> Result<()>;         // upsert por id
    pub async fn delete(&self, id: T::Id) -> Result<()>;           // NotFound si no existe
    pub async fn exists(&self, id: T::Id) -> Result<bool>;
}

La cota T::Id: Into<Value> es necesaria porque Aggregate::Id (§7.1) es un tipo asociado libre y el puerto solo habla Value. El núcleo provee From para Uuid, String, &str, bool, i64 e i32; un identificador exótico necesita su propio From. Repo<T> implementa FromContainer (§6.3), así que #[service] lo inyecta sin registro por agregado: lee el valor Db que App::build() deja en el contenedor.

/// Adaptador activo, inyectable por tipo (RF-022). Lo registra `App::build()`.
pub struct Db(pub Arc<dyn DbAdapter>);

Por debajo habla con un puerto object-safe. El núcleo no conoce ningún driver (RA-014): solo este trait, un valor neutro y una fila neutra.

// rdd-core
pub enum Value {
    Null, Bool(bool), I64(i64), F64(f64),
    Text(String), Bytes(Vec<u8>), Uuid(uuid::Uuid), Json(serde_json::Value),
}

/// Fila neutra: columna → valor. Conserva el orden de inserción, pero el orden no
/// es contractual: `from_row` lee por nombre.
pub struct Row { /* … */ }

pub trait DbAdapter: Send + Sync + 'static {
    fn name(&self) -> &'static str;
    fn get<'a>(&'a self, table: &'a str, id_column: &'a str, id: &'a Value)
        -> BoxFuture<'a, Result<Option<Row>>>;
    fn all<'a>(&'a self, table: &'a str) -> BoxFuture<'a, Result<Vec<Row>>>;
    fn save<'a>(&'a self, table: &'a str, columns: &'a [&'a str], values: &'a [Value])
        -> BoxFuture<'a, Result<()>>;
    fn delete<'a>(&'a self, table: &'a str, id_column: &'a str, id: &'a Value)
        -> BoxFuture<'a, Result<bool>>;
}

La vida 'a es explícita y común a todos los argumentos: con BoxFuture<'_> el elisión la ata solo a &self, y el async move del adaptador no podría capturar table ni id. Sigue siendo object-safe.

id_column va explícito en get y delete porque un motor SQL necesita el nombre de la columna para el WHERE y no puede adivinarlo: Persist::COLUMNS[0] puede llamarse task_id, no id. Repo<T> lo pasa desde T::COLUMNS[0]; los motores documentales y KV lo ignoran (usan _id o la clave). all no recibe columnas y hace SELECT *, así que el orden de Row no es contractual: from_row lee por nombre y las columnas de más se ignoran.

El puerto tiene cuatro operaciones, no seis: find/get se distinguen en Repo<T> (una devuelve Option, la otra NotFound) y exists se resuelve con get. Así cada motor implementa menos y hay menos superficie que portar.

En save, columns[0] y values[0] SON el identificador; es la convención que permite el upsert sin firmar un método por motor.

12.3 Transacciones y concurrencia

Fuera de alcance en 0.x. Cada save es autocommit. La concurrencia optimista (columna version) y #[transactional] son candidatos posteriores. El puerto NO expone transacciones: exigirlas obligaría a todos los motores a soportarlas, y Redis no las ofrece como un SQL.

12.6 Registro de adaptadores y arranque

RA-014 prohíbe al núcleo conocer un driver, así que el núcleo tampoco puede saber qué crate implementa mongodb://. La solución es la misma que RP-012 usa para la plataforma por defecto: un registro global en el núcleo que la fachada puebla.

// rdd-core::db
pub type AdapterFactory = fn(String) -> BoxFuture<'static, Result<Arc<dyn DbAdapter>>>;

/// Declara un motor conocido aunque no esté instalado: da el mensaje de RF-111.
pub fn declare(schemes: &[&'static str], crate_name: &'static str, feature: &'static str);
/// Instala la factoría de un motor compilado en la fachada.
pub fn install(scheme: &str, factory: AdapterFactory);
/// Resuelve el esquema de la URL; error de arranque si no hay factoría.
pub fn factory_for(url: &str) -> Result<AdapterFactory>;

declare la llama la fachada para los seis motores, con o sin feature; install solo para los compilados. Así el mensaje de un esquema no instalado nombra crate y feature exactos, y añadir un motor nuevo no toca el núcleo (RF-185): basta su crate y una línea en la fachada.

Las features de la fachada son axum y sqlite por defecto, más una por motor opcional (postgres, y las que se añadan con cada crate). Activar la feature trae el crate como dependencia optional, re-exporta su adaptador y hace que rdd::run_main llame a su register(). Es run_main —el código que expande #[rdd::main]— y no un inicializador global, porque la fachada solo puede ejecutar código en el camino que ella misma genera, igual que RP-012 con la plataforma. register() es idempotente y hace ambas cosas: declare para sus esquemas e install de su factoría.

13. Integración con Prisma

13.1 Decisión

El cliente prisma-client-rust no se usa: su repositorio principal indica que no recibe mantenimiento y su última versión soportada de Prisma es antigua. 14.2 Archivos que genera rdd g module tasks

El árbol de módulo de §5, bajo src/modules/tasks/, contiene solo las cuatro capas estándar y sus archivos funcionales (RF-001, RF-003, RF-005). domain/ define Task con Aggregate + Persist (§12.2) y el puerto async TaskRepository; application/ contiene los casos de uso CRUD, genéricos sobre el puerto; infrastructure/ implementa el puerto envolviendo Repo<Task>; presentation/ contiene los DTOs HTTP y #[controller("/tasks")] con los cinco verbos (list, get, create, update, remove). Los tests unitarios se mantienen inline con #[cfg(test)], sin una carpeta adicional.

Los nombres que genera el CLI, con tasks como ejemplo: TasksController, TasksUseCases, TasksRepository (adaptador), TaskRepository (puerto), Task (agregado), TaskResponse (DTO de salida), CreateTaskDto, UpdateTaskDto, QueryTaskDto y MAX_TITLE_LEN.

domain/mod.rs re-exporta Task, TaskError y TaskRepository, y todos los consumidores importan desde ahí, no desde el archivo: use …::domain::Task;. Es la API pública de la capa (RA-004) y lo que evita el aviso de unused_imports que un re-export nadie usa produce en un crate binario, rompiendo RF-007. Las otras tres capas solo declaran sus módulos: no tienen tipos que cruzen la frontera tanto como el dominio.

El identificador es uuid::Uuid y lo genera Task::new (§7.2): el puerto no tiene next_id() porque asignar ids es responsabilidad del motor o del agregado, no del caso de uso. Task NO deriva Deserialize (RF-031): la entrada HTTP son los DTOs de presentation/, nunca el agregado.

infrastructure/tasks_repository.rs no tiene almacén propio, ni static, ni shared(), ni new() sin argumentos: recibe el Repo<Task> ya resuelto (TasksRepository::new(repo)). El aislamiento de los tests lo dan MemoryBackend y TestApp (RF-160), no un estático global compartido entre tests.

modules/tasks/mod.rs es la raíz de composición: declara las cuatro capas, define pub type TasksService = TasksUseCases<TasksRepository>;, escribe a mano impl FromContainer e impl FromRequest para TasksService (§6.3) y expone module() con providers: []. Es el único archivo del módulo que nombra a la vez infrastructure/ y rdd::http, y por eso vive fuera de las cuatro capas (§17).

TasksUseCases<R: TaskRepository> NO lleva tipo por defecto: un = TasksRepository obligaría a application/ a importar infrastructure/, que RA-002 prohíbe. El controller usa el alias TasksService, que es API pública del módulo (RA-004) y no nombra el adaptador, así que RA-003 tampoco se viola.

El puerto declara fn … -> impl Future<Output = …> + Send y el adaptador lo implementa con async fn, igual que FromRequest (§6.3): un async fn en el trait no garantiza un futuro Send, que la plataforma sí exige.

Los tests del caso de uso viven en modules/tasks/mod.rs, no en application/: necesitan el adaptador real y MemoryBackend, y solo la raíz de composición puede nombrar ambos (RA-002). Cada test construye su propio Repo::new(Arc::new( MemoryBackend::new())), así que no hay estado compartido (RF-160). Las invariantes del agregado se prueban en domain/task.rs.

tests/acceptance.rs incluye src/ por #[path] porque un test de integración no puede importar el crate binario; así crate::modules::… y crate::app_* resuelven igual que en main.rs y no hay que duplicar el cableado. El test monta la app sin .database(url), de modo que App::build() registra MemoryBackend (§12.6) y la aceptación corre sin servidor; el CRUD contra PostgreSQL real es la aceptación de todo-app-ddd (§25.6), no la del scaffold.

25.3 Persistencia

Task implementa Aggregate (§7.1) con type Id = Uuid y Persist (§12.2) con TABLE = "tasks" y COLUMNS = ["id", "title", "done"]. Mientras #[aggregate] no esté implementada (RF-006), esas dos impls se escriben a mano en modules/tasks/domain/task.rs; la macro las sustituirá sin cambiar el resto del módulo. from_row lee por nombre (row.value("id")?.as_uuid()?), porque el orden de Row no es contractual (§12.1).

El puerto TaskRepository vive en domain/tasks_repository.rs y es async: declara fn … -> impl Future<Output = …> + Send, que es la forma real de FromRequest (§6.3), y el adaptador lo implementa con async fn. Un async fn en la declaración del trait no garantiza que el futuro sea Send, y los handlers de la plataforma sí lo exigen; el + Send es lo que lo garantiza. El caso de uso es genérico sobre el puerto, así que no necesita object-safety ni el crate async_trait. El adaptador TasksRepository vive en infrastructure/tasks_repository.rs, envuelve Repo<Task> y no conoce ningún driver (RA-007). Cambiar DATABASE_URL a otro motor no toca ni el caso de uso ni el controller (RF-185).

// modules/tasks/infrastructure/tasks_repository.rs
pub struct TasksRepository { repo: Repo<Task> }

impl TasksRepository {
    pub fn new(repo: Repo<Task>) -> Self { Self { repo } }
}

impl TaskRepository for TasksRepository {
    async fn list(&self) -> Result<Vec<Task>> { self.repo.all().await }
    async fn get(&self, id: Uuid) -> Result<Task> { self.repo.get(id).await }
    async fn save(&self, task: &Task) -> Result<()> { self.repo.save(task).await }
    async fn remove(&self, id: Uuid) -> Result<()> { self.repo.delete(id).await }
}

No hay shared() ni new() con un static global: el aislamiento de los tests lo dan MemoryBackend y TestApp (RF-160), y el Repo<Task> se inyecta desde el contenedor (§12.1) a través de las dos impls de modules/tasks/mod.rs (§6.3, §17).

25.4 Arranque

El main.rs es el de §14.3. La URL viene solo del entorno (RF-063), en un .env no versionado:

# todo-app-ddd/.env — NO se commitea
DATABASE_URL=postgres://postgres:<clave>@localhost:5433/todo_db

Puerto 5433, no 5432. En la máquina de desarrollo hay dos PostgreSQL: el servicio nativo de Windows (postgresql-x64-17) y Docker. Los dos publican 5432 y el nativo gana la conexión, así que un contenedor en 5432 es inalcanzable desde el host — el síntoma es un FATAL de autenticación con mensajes en un codepage que no es UTF-8, que sqlx reporta como «non-UTF-8 string for its error message». La instancia de pruebas es el contenedor rdd-pg (postgres:15-alpine, BD todo_db) publicado en 5433; ni el servicio nativo ni todo-pg se tocan.

App::new().database(url) no conecta: .run() llama a connect().await, que resuelve el esquema postgres:// por el registro de §12.6 y conecta el pool antes de abrir el socket (RF-111, RF-119). Sin .env la app no arranca en memoria: cae en la URL de respaldo de §14.3, que lleva CAMBIAR por contraseña y falla al conectar. │   ├── middleware/             # transversal de la app, no es un módulo
│   │   ├── mod.rs
│   │   ├── jwt.rs              # JwtMiddleware: identifica, no rechaza
│   │   ├── require_auth.rs     # RequireAuth: 401 si no hay sesión
│   │   └── require_role.rs     # RequireRole: 403 si el rol no alcanza
│   └── modules/
│       ├── users/              # las cuatro capas de §5
│       └── tasks/              # el del CLI, con los guards puestos
└── tests/acceptance.rs         # 401, 403, 429 y preflight

src/middleware/ y config/jwt_config.rs los añade el demo, no el CLI: no todos los proyectos necesitan middlewares propios y el scaffold no debe generar configuración de seguridad por omisión (RF-006, RN-030). Son código funcional, no placeholders, así que RF-004 no se relaja. Ningún archivo del demo queda en blanco: cada uno lleva código y un comentario que explica qué pinta ahí.

Cómo no violar RA-004. JwtMiddleware es transversal: lo mismo lo usa users que tasks, y un módulo no puede importar archivos internos de otro. Por eso vive fuera de modules/ y toma Session y Role de la API pública del módulo users —lo que users/mod.rs re-exporta con pub use—, que es exactamente lo que RA-004 permite. tasks/presentation/ importa Session por esa misma vía.

26.3 La receta JWT (a nivel de aplicación)

Cuatro piezas, todas con API que ya existe:

  1. JwtMiddleware implementa Middleware (§11.1) y es global. Lee

Authorization: Bearer <token> y, si es válido, mete la identidad en las extensiones (req.extensions_mut().insert(session), RF-083). Si no hay cabecera, o el token es inválido o expiró, sigue igual sin sesión: no rechaza. Identifica, no autoriza.

  1. RequireAuth es el que rechaza: montado por controller, devuelve

Err(Error::Unauthorized) sin llamar a next (RF-082) cuando no hay sesión en las extensiones, y el núcleo lo materializa como 401 con Problem Details (§10.3).

  1. Ext<Session> en el handler lee la identidad. El controller no vuelve a

mirar la cabecera.

  1. RequireRole lee la sesión y devuelve Err(Error::Forbidden) → 403 si el

rol no alcanza. Se monta por ruta con #[middleware(RequireRole::new(Role::Admin))] (§11.4, RF-086).

Separar identificar (1) de exigir (2) lo fuerza el orden de RF-080 —global → módulo → controller → ruta—: un JWT global que rechazara sin token dejaría fuera /auth/register, /auth/login y /health, y un JWT de controller correría después del RateLimit global, que entonces no tendría identidad con qué contar (RF-109). Con el desdoble, RateLimit ve la sesión cuando la hay y RequireAuth decide qué rutas la exigen.

// main.rs — los tres globales, en este orden (§26.4)
let tokens = modules::users::tokens();
App::new()
    .middleware(Cors::from_config().map_err(|err| Error::Internal(err.into()))?)
    .middleware(JwtMiddleware::new(Arc::new(tokens.clone())))
    .middleware(
        RateLimit::new(100, Duration::from_secs(60), rate_key)
            .map_err(|err| Error::Internal(err.into()))?,
    )
    .module(modules::users::module(tokens))

CorsConfigError y RateLimitConfigError no tienen From hacia rdd::Error, así que el ? del snippet necesita el map_err: son fallos de configuración, o sea 500 (RF-041), y no un 400 que culparía al cliente de algo que puso el operador.

El codec se construye una vez en main.rs y se le pasa al módulo, que lo registra como singleton del contenedor. No lo construye la fábrica del módulo: std::env::set_var es unsafe en edition 2024 y el workspace prohíbe unsafe (RF-143), así que un test no puede inyectar JWT_SECRET por el entorno. Recibirlo como parámetro es lo que deja probar el login con un secreto de prueba.

#[controller("/tasks")]
#[middleware(RequireAuth)]
impl TasksController {
    #[get("/")]
    async fn list(
        svc: TasksService,
        session: Ext<Session>,
        query: Query<QueryTaskDto>,
    ) -> Result<Vec<TaskResponse>> {
        svc.list_of(session.id, query.q, query.done).await
    }

    #[delete("/:id")]
    #[middleware(RequireRole::new(Role::Admin))]
    async fn remove(svc: TasksService, session: Ext<Session>, id: Path<Uuid>) -> Result<()> {
        svc.remove_of(session.id, *id).await
    }
}

El dueño viaja en el session del handler al caso de uso, no en el DTO: si viniera en el cuerpo, el cliente elegiría de quién es la tarea.

El secreto y la expiración vienen solo del entorno (JWT_SECRET, JWT_TTL_SECS), nunca del código ni de rdd.toml (RF-063, RN-030). Las contraseñas se guardan con argon2, nunca en claro ni con un hash reversible. User no deriva Deserialize (RF-031): la entrada son RegisterDto y LoginDto. Las dependencias del demo —jsonwebtoken y argon2— no las arrastra el núcleo (RA-011, RA-014).

De dónde sale el admin. RegisterDto NO lleva campo role: dejar que el cliente lo elija sería una escalada de privilegios. El registro nace siempre user, salvo que el correo coincida con ADMIN_EMAIL (tercera variable de jwt_config.rs, comparada sin distinguir mayúsculas). Es la única vía de bootstrap del demo: no hay endpoint para cambiar el rol ni un usuario sembrado con contraseña conocida en el SQL. Sin ADMIN_EMAIL puesta, nadie es admin y la comprobación 4 de §26.6 se verifica solo en su mitad 403.

Identificar y autorizar son dos pasos. El codec de tokens es un puerto del dominio users (TokenCodec, con issue y verify); su adaptador HS256 vive en users/infrastructure/ y se publica con pub use desde users/mod.rs, que es lo que RA-004 permite importar a src/middleware/jwt.rs. Así el Claims del JWT se escribe una sola vez: si emisión y verificación tuvieran cada una su copia, cambiar un campo rompería el login en silencio.

26.4 Orden de los middlewares

Cadena efectiva de una ruta protegida. Los tres primeros son globales y se registran en ese orden; RequireAuth es de controller y RequireRole de ruta (RF-080):

CORS ─► JwtMiddleware ─► RateLimit ─► [módulo] ─► RequireAuth ─► RequireRole ─► handler
  • CORS primero (RF-085): el preflight OPTIONS se responde 204 sin pasar por la autenticación (RF-094). Invertir el orden rompe el navegador: el preflight viaja sin credenciales, así que un 401 ahí impide la petición real para siempre.
  • RateLimit después de identificar: su clave es la identidad autenticada (user:<id>), no una cabecera que el cliente pueda cambiar (RF-109). Sin identidad la clave es anonymous, de modo que registro y login también quedan limitados.
  • El 429 lleva Problem Details, Retry-After y RateLimit-* (RF-107). CORS lo cubre porque es global y envuelve también el fallback (RF-081).

RequireAuth se monta por controller, no global: /auth/register, /auth/login y /health tienen que seguir siendo públicos. JwtMiddleware sí es global porque solo identifica y no rechaza nada (§26.3).

26.5 Persistencia

SQLite (RF-111), el motor predeterminado del CLI: no necesita servidor, así que el demo se verifica completo sin Docker ni red. User y Task implementan Aggregate + Persist a mano (RF-006) sobre Repo<T>. users guarda id, email, password_hash, role; tasks gana owner_id para que cada quien vea solo las suyas. Filtrar por dueño es responsabilidad del caso de uso, no del controller: el controller no decide nada (§5.1). Ninguna columna temporal (RF-187, V15).

0002_users.sql crea users y añade owner_id a tasks con ALTER TABLE. Es seguro porque rdd migrate lleva la cuenta en _sqlx_migrations y no reaplica (§14.1); el demo parte de una base vacía, así que no hay filas anteriores que queden sin dueño. email lleva UNIQUE: la carrera entre dos registros del mismo correo la resuelve la base, y el adaptador la traduce a 409 (RF-042).

Rol y dueño son dos autorizaciones distintas. RequireRole decide si la identidad puede ejecutar la operación (DELETE exige admin); el caso de uso decide si el recurso es suyo. Un admin tampoco borra tareas ajenas: recibe 404, igual que cualquier otro, porque el recurso no existe *para él* (§26.6, comprobación 8).
