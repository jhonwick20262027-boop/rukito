Arquitectura del Framework rdd

Principios Fundamentales

El framework rdd sigue un diseño limpiamente separado entre núcleo y plataformas:

Regla de oro (RA-001): Las reglas de negocio viven en el aggregate. El controller nunca decide.

Rasgos clave:

  • Core HTTP neutral: Tipos HTTP basados en crate `http`, no en Axum ni hyper directamente
  • Plataforma adaptador: Axum es la plataforma por defecto, hyper es alternativa intercambiable
  • Sin dependencias circulares: rdd-core no conoce Axum ni hyper; las plataformas dependen solo del núcleo
  • DI limitada: Sin reflexión en tiempo de ejecución; las macros generan constructores tipados
  • Errores Problem Details: Todas las respuestas siguen RFC 9457 (problem+json)

Workspace estructura:

crates/
├── rdd/            # FACHADA: re-exporta rdd-core + macros + plataforma por feature
├── rdd-core/       # Núcleo: App, DI, middlewares, RouteDef, trait Platform
├── rdd-axum/       # Plataforma por defecto
├── rdd-cors/       # Middleware CORS (RF-090 a RF-099)
├── rdd-sqlite/     # Adaptador SQLite (sqlx)
├── rdd-postgres/   # Adaptador PostgreSQL (sqlx)
└── rdd-cli/        # Binario `rdd`

Workspace del Framework

El repositorio del framework contiene todos los crates necesarios:

  • rdd-core: Núcleo puro, sin Axum, sin hyper, sin drivers SQL
  • rdd-macros: Procedural macros para controller, service, aggregate, middleware
  • rdd-axum: Plataforma HTTP por defecto sobre Axum
  • rdd-hyper: Plataforma propia basada en hyper (fase 0.5)
  • rdd-cors, rdd-logger: Middlewares oficiales
  • rdd-platform-tests: Suite de conformidad para todas las plataformas
  • rdd-db-tests: Suite para adaptadores de base de datos
  • rdd-postgres, rdd-mysql, etc.: Adaptadores por motor
  • rdd-cli: Interfaz de línea de comandos

Interfaz de Plataforma (Modelo Adaptador)

El núcleo define qué es una aplicación HTTP (rutas como datos, middlewares compuestos). La plataforma solo sabe servirla.

Tipo HttpApp:

// rdd-core
pub type Request   = http::Request;
pub type Response  = http::Response;
pub type BoxHandler = Arc BoxFuture<'static, Response> + Send + Sync>;

pub struct RouteDef {
    pub method:  Method,
    pub path:    String,              // Siempre sintaxis "/:id" (RP-003)
    pub handler: BoxHandler,           // incluye su cadena completa de middlewares
}

pub struct HttpApp {
    pub routes:   Vec,
    pub fallback: BoxHandler,         // decide 404 o 405 (RP-007)
    pub limits:   Limits,
}
impl HttpApp {
    pub async fn dispatch(&self, req: Request) -> Response;
}

Trait Platform:

// rdd-core
pub trait Platform: Send + 'static {
    fn name(&self) -> &'static str;
    fn serve(self, app: HttpApp, listener: TcpListener, shutdown: ShutdownSignal)
        -> BoxFuture<'static, Result<()>>;
}

El núcleo provee App::run(addr) usando la plataforma por defecto (Axum), o App::run_on(plataforma, addr) para cualquiera implementada.

Rate limiting

RateLimit es un middleware del núcleo, compatible con todas las plataformas. Define el máximo de peticiones por cliente y ventana; la aplicación proporciona la función que identifica al cliente.

use std::time::Duration;
use rdd::prelude::*;

struct AuthenticatedUser { id: u64 }

let limiter = RateLimit::new(60, Duration::from_secs(60), |req| {
    req.extensions()
        .get::<AuthenticatedUser>()
        .map(|user| format!("user:{}", user.id))
        .unwrap_or_else(|| "anonymous".to_owned())
}).expect("configuración válida");

let app = App::new().middleware(limiter);
  • Al exceder el límite responde 429 Too Many Requests como Problem Details e incluye Retry-After y cabeceras RateLimit-*.
  • El estado es local al proceso, con un máximo predeterminado de 10 000 claves; ajusta la capacidad con with_max_keys.
  • La autenticación debe validar las credenciales e insertar la identidad en las extensiones de la petición antes de este middleware. No uses una cabecera arbitraria ni confíes en X-Forwarded-For salvo que un proxy confiable la establezca.
  • Para varias réplicas, usa rate limiting compartido en el proxy o almacenamiento común.

Consulta los requisitos RF-105 a RF-109 en la especificación (§11.7).
