Subida de archivos en rdd

Guardar archivos es una dependencia de salida, no una ruta ni una tabla. rdd-upload define el puerto ObjectStorage, la política de claves y un MemoryStorage; las features de nube añaden un adaptador REST por proveedor. La app decide qué controlador recibe el archivo y qué clave le asigna: el framework no monta ninguna ruta ni lee credenciales por su cuenta.

Activar la feature

El puerto y el storage en memoria vienen con upload; cada nube es una feature independiente:

# Solo el puerto y MemoryStorage
rdd = { package = "rdd-framework", version = "0.1", features = ["upload"] }

# Con AWS S3, Azure Blob o Google Cloud Storage
rdd = { package = "rdd-framework", version = "0.1", features = ["upload-aws"] }
rdd = { package = "rdd-framework", version = "0.1", features = ["upload-azure"] }
rdd = { package = "rdd-framework", version = "0.1", features = ["upload-gcs"] }

Todo se importa desde rdd::upload. No hay SDK de nube, ni Tower, ni drivers: cada adaptador firma sus peticiones a mano sobre un cliente HTTP con TLS.

El puerto

OperaciónQué hace
put(key, body, options)Guarda o sobrescribe y devuelve la metadata; PutOptions lleva content_type, cache_control y metadatos de usuario.
get(key)Devuelve el objeto completo, o None si la clave no existe.
head(key)Solo la metadata, o None si no existe.
delete(key)Borra; es idempotente y un 404 del proveedor no es error.

Una clave se valida con ObjectKey::parse: de 1 a 1024 bytes, sin / inicial, sin segmentos vacíos, . ni .., sin \ ni controles. Cada segmento se codifica al firmar, así que un adaptador nunca interpola texto del cliente en la ruta. Para empezar sin infraestructura:

use std::sync::Arc;
use rdd::upload::{MemoryStorage, ObjectStorage};

let storage: Arc<dyn ObjectStorage> = Arc::new(MemoryStorage::with_max_bytes(8 * 1024 * 1024));

Recibir el archivo en un controller

El cuerpo llega completo con el extractor Bytes y el nombre va por cabecera. La clave la construye el caso de uso con la sesión y un Uuid del servidor, nunca el cliente:

use rdd::prelude::*;
use rdd::upload::PutOptions;

#[controller("/files")]
#[middleware(RequireAuth)]
impl FilesController {
    #[post("/", status = 201)]
    async fn upload(
        svc: FilesService,
        session: Ext<Session>,
        x_file_name: Header<String>,
        content_type: Header<String>,
        body: Bytes,
    ) -> Result<FileResponse> {
        svc.upload_of(session.id, x_file_name.into_inner(), content_type.into_inner(), body)
            .await
    }
}

El límite de cuerpo de la app corre antes del handler: un archivo mayor que App::body_limit es 413 y no llega al storage. El adaptador también rechaza un objeto mayor que su max_object_bytes (64 MiB por defecto).

AWS S3

Firma SigV4 con el SHA-256 del cuerpo, la región y x-amz-security-token si hay token de sesión. Sin endpoint usa estilo virtual-host; con endpoint o force_path_style(true) usa /{bucket}/{key}.

VariablePor defecto
AWS_S3_BUCKETobligatoria
AWS_ACCESS_KEY_IDobligatoria
AWS_SECRET_ACCESS_KEYobligatoria
AWS_SESSION_TOKENopcional
AWS_REGIONus-east-1
AWS_ENDPOINT_URLAWS; con valor fuerza path-style
AWS_S3_FORCE_PATH_STYLEtrue con endpoint, false sin él
AWS_MAX_OBJECT_BYTES67108864
use rdd::upload::{Credentials, ObjectStorage, S3Config, S3Storage};

let storage: std::sync::Arc<dyn ObjectStorage> = std::sync::Arc::new(
    S3Storage::new(
        S3Config::new("mi-bucket", Credentials::new(access_key, secret_key))
            .region("eu-west-1")
            .endpoint("http://127.0.0.1:9000") // MinIO; ausente = AWS
            .force_path_style(true),
    )?,
);

// O todo desde el entorno:
let storage = S3Storage::from_env()?;

Azure Blob

Firma SharedKey sobre la cadena canónica, envía x-ms-date y x-ms-version, y en put usa x-ms-blob-type: BlockBlob. El endpoint por defecto es https://{cuenta}.blob.core.windows.net; Azurite se configura con http://127.0.0.1:10000/{cuenta}.

VariablePor defecto
AZURE_STORAGE_ACCOUNTobligatoria
AZURE_STORAGE_ACCESS_KEYobligatoria
AZURE_STORAGE_CONTAINERobligatoria
AZURE_STORAGE_ENDPOINThttps://{cuenta}.blob.core.windows.net
AZURE_STORAGE_MAX_OBJECT_BYTES67108864
use rdd::upload::{AzureBlobConfig, AzureBlobStorage};

let storage = AzureBlobStorage::new(
    AzureBlobConfig::new(account, access_key, "mi-contenedor")
        .endpoint("http://127.0.0.1:10000/devstoreaccount1"),
)?;

// O todo desde el entorno:
let storage = AzureBlobStorage::from_env()?;

Google Cloud Storage

Usa la API XML con una clave HMAC de interoperabilidad (no OAuth2, ni cuenta de servicio JSON, ni ADC) y firma V4: GOOG4-HMAC-SHA256, ámbito {fecha}/auto/storage/goog4_request y cabeceras x-goog-date y x-goog-content-sha256. La ruta es /{bucket}/{key}, así que el mismo código sirve contra storage.googleapis.com o un emulador.

VariablePor defecto
GCS_BUCKETobligatoria
GCS_HMAC_ACCESS_IDobligatoria
GCS_HMAC_SECRETobligatoria
GCS_ENDPOINThttps://storage.googleapis.com
GCS_MAX_OBJECT_BYTES67108864
use rdd::upload::{GcsConfig, GcsStorage};

let storage = GcsStorage::new(
    GcsConfig::new("mi-bucket", access_id, secret),
)?;

// O todo desde el entorno:
let storage = GcsStorage::from_env()?;

Precedencia y errores

  • Un valor fijado en el constructor gana sobre su variable; una variable ausente con defecto no secreto usa el defecto.
  • Un secreto ausente es un error de arranque que nombra la variable. Secret no revela su valor en Debug ni en Display.
  • Un endpoint que no sea https se rechaza; http solo se acepta de forma explícita para un emulador.
  • Ningún adaptador registra credenciales, firmas ni Authorization.
  • No hay reintentos ni failover: un fallo del proveedor vuelve como Error::internal con su estado y su código. La política de reintentos es de la app.

El demo: --upload

example/todo-app --upload monta POST /files, GET /files/:id y DELETE /files/:id. Solo la metadata viaja en JSON; la descarga binaria queda fuera de esta fase. La política sale del entorno:

VariablePor defectoEfecto
UPLOAD_DRIVERmemorymemory, aws, azure o gcs
UPLOAD_MAX_BYTES8388608Límite del objeto y del cuerpo de la petición
cargo run -p todo-app -- --upload

TOKEN=... # JWT de /auth/login
curl -s -X POST localhost:3000/files \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-File-Name: notas.txt" \
  -H "Content-Type: text/plain" \
  --data-binary @notas.txt            # 201 {"id":"...","size":123,"content_type":"text/plain"}

curl -s localhost:3000/files/<id> -H "Authorization: Bearer $TOKEN"   # metadata
curl -s -X DELETE localhost:3000/files/<id> -H "Authorization: Bearer $TOKEN"  # 204

La clave es files/{owner_id}/{id} y sale de la sesión, así que el usuario B recibe 404 al leer o borrar el archivo de A. Sin --upload las tres rutas no existen.

Límites de esta fase

  • Los cuerpos viajan en memoria: no hay multiparte, reanudación ni streaming saliente.
  • No hay URLs prefirmadas, listado de objetos ni administración de buckets o contenedores.
  • No hay identidades de nube (IMDS, managed identity, OAuth2/ADC) ni SDKs oficiales.

Requisitos completos: RF-269 a RF-278 en la especificación (§10.13).
