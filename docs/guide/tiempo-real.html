Tiempo real con rdd-socket

rdd ofrece un canal WebSocket opcional sobre el mismo servidor: el núcleo decide el handshake y la plataforma transporta las tramas. Las salas y la presencia viven en rdd-socket. El REST sigue siendo el camino de escritura: los eventos nacen en los controllers y salen por el canal.

WebSocket nativo, no Socket.IO

El canal habla WebSocket estándar (RFC 6455) con tramas de texto que tú defines. No implementa Socket.IO: no hay handshake Engine.IO, ni polling, ni eventos con nombre, ni reconexión automática. Un cliente de Socket.IO no puede conectarse a /ws/tasks; usa un cliente WebSocket normal y decide el formato de los mensajes.

Si lo que necesitas son datos reactivos de GraphQL, las suscripciones ya viajan por SSE y no hace falta abrir un WebSocket. Consulta la guía GraphQL.

El puerto del núcleo

Un canal es un SocketHandler: authorize decide antes del 101 y handle vive mientras la conexión vive. La plataforma solo traduce tramas; nunca interpreta los mensajes.

pub trait SocketHandler: Send + Sync + 'static {
    /// Antes del 101; un Err se materializa en Problem Details (RF-198).
    fn authorize(&self, _ctx: &SocketContext) -> Result<()> { Ok(()) }

    /// Vive mientras la conexión vive; al volver, el canal cierra con 1000.
    fn handle(
        &self,
        ctx: SocketContext,
        conn: Box<dyn SocketConnection>,
    ) -> BoxFuture<'static, Result<()>>;
}

pub enum SocketMessage {
    Text(String),
    Binary(Bytes),
    Ping(Bytes),
    Pong(Bytes),
    Close(Option<u16>, String),
}
  • SocketContext lleva path, params, el container de la app y las extensions que dejaron los globales.
  • authorize corre después de la cadena global completa (CORS, JWT, RateLimit) y antes del 101. Un rechazo es una respuesta HTTP normal, sin cambio de protocolo.

Registrar un canal

El canal se declara en App, no en un módulo, y no participa del 404/405 del fallback:

# La feature `socket` trae el hub de §10.5 y el transporte WS de `rdd-axum`.
rdd = { package = "rdd-framework", version = "0.1", features = ["socket"] }
let feed = modules::tasks::TaskFeed::new();

let app = App::new()
    .middleware(Cors::from_config()?)
    .middleware(JwtMiddleware::new(keys))
    .middleware(RateLimit::new(100, Duration::from_secs(60), rate_key)?)
    // El handler y el controller comparten el mismo hub.
    .provide(feed.clone())
    .socket("/ws/tasks", feed)
    .module(tasks::module());

.socket(...) existe con o sin la feature; esa feature añade el hub y el transporte. Una plataforma sin soporte de upgrades responde 501 y las pruebas del canal quedan exentas.

El handler del demo

TaskFeed exige sesión, se suscribe a la sala y reenvía cada evento; un suscriptor atrasado se cierra con 1013 en vez de perder mensajes en silencio:

use rdd::http::BoxFuture;
use rdd::prelude::*;
use rdd::{Hub, Lagged, Payload};

#[derive(Clone)]
pub struct TaskFeed {
    hub: Hub,
}

impl SocketHandler for TaskFeed {
    /// Sin sesión no hay 101: el handshake responde 401 (RF-198).
    fn authorize(&self, ctx: &SocketContext) -> Result<()> {
        ctx.ext::<Session>().map(|_| ()).ok_or(Error::Unauthorized)
    }

    fn handle(
        &self,
        _ctx: SocketContext,
        mut conn: Box<dyn SocketConnection>,
    ) -> BoxFuture<'static, Result<()>> {
        let hub = self.hub.clone();
        Box::pin(async move {
            let mut sub = hub.subscribe("tasks");
            conn.send(SocketMessage::Text(
                serde_json::json!({ "type": "ready", "topic": "tasks" }).to_string(),
            ))
            .await?;

            loop {
                tokio::select! {
                    incoming = conn.recv() => match incoming {
                        Some(Ok(SocketMessage::Close(_, _))) | None => break,
                        Some(Ok(_)) => {}
                        Some(Err(err)) => return Err(err),
                    },
                    event = sub.recv() => match event {
                        Ok(Payload::Text(text)) => {
                            conn.send(SocketMessage::Text(text)).await?;
                        }
                        Ok(Payload::Json(value)) => {
                            conn.send(SocketMessage::Text(value.to_string())).await?;
                        }
                        Ok(Payload::Binary(bytes)) => {
                            conn.send(SocketMessage::Binary(bytes)).await?;
                        }
                        Err(Lagged(_)) => {
                            conn.close(1013, "cliente lento".to_owned()).await;
                            return Ok(());
                        }
                    },
                }
            }
            Ok(())
        })
    }
}

El hub: salas y presencia

let hub = Hub::new();
let mut sub = hub.subscribe("tasks");          // entrar a la sala

hub.broadcast("tasks", serde_json::json!({ "type": "created" })).await;
assert_eq!(hub.members("tasks").len(), 1);     // presencia: suscripciones vivas

match sub.recv().await {
    Ok(Payload::Json(value)) => println!("{value}"),
    Ok(Payload::Text(text)) => println!("{text}"),
    Ok(Payload::Binary(bytes)) => println!("{} bytes", bytes.len()),
    Err(Lagged(skipped)) => eprintln!("perdí {skipped} mensajes"),
}
  • subscribe(topic) devuelve una Subscription viva mientras se sostenga; soltarla es salir de la sala y members lo refleja.
  • broadcast no bloquea ni serializa la entrega: cada suscripción tiene su propio anillo de 64 mensajes.
  • El hub es local al proceso: sin historial, sin persistencia y sin coordinación entre réplicas. Para varias instancias hace falta un broker externo, que queda fuera del framework.
  • Se registra como singleton en el contenedor; un handler lo obtiene por ctx.container o por inyección.

Handshake, límites y cierres

SituaciónResultado
Cadena global completa y authorize en Ok101 Switching Protocols y handle
Un global o authorize rechazanProblem Details 401/403/429; no hay 101
handle termina en OkCierre 1000
Error o panic en handleCierre 1011; el panic se aísla por conexión
Apagado de la appCierre 1001 dentro de shutdown_grace
Mensaje entrante mayor a 1 MiBCierre 1009 sin entregarlo al handler
Cliente que no drena la cola de salidaCierre 1013; send devuelve Err

Los límites son Limits::socket_message_limit_bytes (1 MiB) y Limits::socket_outbound_queue (64).

Conectar desde un cliente

El handshake es una petición HTTP más: la identidad viaja en la cabecera Authorization y el JWT global la deja en las extensiones. Un cliente con cabeceras propias (Node, Rust, websocat) funciona directo:

import WebSocket from "ws";

const socket = new WebSocket("ws://127.0.0.1:3000/ws/tasks", {
  headers: { authorization: `Bearer ${process.env.TOKEN}` },
});

socket.on("message", (data) => console.log(JSON.parse(data.toString())));
socket.on("close", (code) => console.log("cierre", code));
websocat -H "Authorization: Bearer $TOKEN" ws://127.0.0.1:3000/ws/tasks

Navegador: new WebSocket() no permite fijar cabeceras, y el JwtMiddleware del demo solo lee Authorization. Para conectar desde una página necesitas algo que ponga la cabecera antes del handshake (un proxy que la inyecte, o un middleware propio que lea una cookie o un ?token= y valide antes de authorize). rdd no trae ese puente: es una decisión de la app, no del framework.

Los eventos del demo

El middleware TaskEvents observa el resultado de las rutas REST y publica en el hub sin tocar los controllers. Los mensajes son JSON:

{ "type": "ready", "topic": "tasks" }
{ "type": "created", "task": { "id": "…", "title": "comprar pan", "done": false } }
{ "type": "updated", "task": { "id": "…", "title": "comprar pan", "done": true } }
{ "type": "deleted", "id": "…" }

Flujo completo: POST /tasks → caso de uso → middleware TaskEvents → hub.broadcast("tasks", …) → todos los clientes conectados a /ws/tasks.

Requisitos completos: RF-194 a RF-204 en la especificación (§10.4 y §10.5); la aceptación del demo está en el anexo §26.7.
